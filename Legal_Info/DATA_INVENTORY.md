## 6. Email verification and recovery data

### Active redesigned client

- Uses Firebase Authentication email verification.
- Uses Firebase Authentication password-reset email.
- Parent email is entered directly into the current sign-in and reset flows.

### Legacy/dormant backend found in the repository

The Firebase Functions source contains a separate username-login recovery design using:

- `users/{uid}`
- `recoveryProfiles/{uid}`
- `mail/{mailId}`
- normalized username
- recovery email
- parent-email verification status
- hashed verification token
- verification expiry and sent timestamps
- password-reset sent timestamp

The current Firestore rules label these collections as legacy and deny all client access, and the redesigned frontend does not call these functions. Deployment status is not established by this source audit. Before publication, choose one account/recovery design and remove or formally document the other. If the legacy functions remain deployed, their processing and retention must be included in the Privacy Policy.

| Reminder times shown in context | React memory; scheduled alert stored by operating system | Morning/evening reminders | Scheduling is local; no push token transmission found | Brushing reminders are cancelled on sign-out and account deletion and replaced when reminders are saved |
| Notification payload | Operating-system notification schedule (`type`, morning/evening period, title/body) | Route a tap to brushing and associate completion with a reminder | No Expo push transmission found; followed completion is later recorded in Firebase | Dismissed and cancelled on sign-out and account deletion; replaced when reminders are saved |

Security observation: the Remember Me feature and all parent-email persistence have been removed. A startup privacy migration deletes the legacy AsyncStorage key without reading it. AsyncStorage stores only the non-sensitive interface-language code; no application password or parent email is stored locally.

## 10. Data flows

### Registration

1. Parent enters child username, parent email, password, and child age.
2. Password and email are sent to Firebase Authentication.
3. Firebase returns a UID.
4. The app creates linked `parents`, `children`, and `usernames` Firestore documents.
5. Firebase sends the parent-email verification message.
6. No verifiable parental-consent record is currently created.

### Normal application use

1. The child/parent signs in through Firebase Authentication.
2. The application retrieves the child profile from Firestore.
3. Brushing, games, rewards, usage time, logins, activities, and reminder-following update the child document.
4. An administrator can retrieve all child summaries through an admin-only Firestore query.

### Notifications

1. The app requests operating-system notification permission.
2. Morning/evening notifications are scheduled locally.
3. Tapping a notification opens the brushing screen.
4. Completing the matching brushing session within one hour increments `remindersFollowed` and stores the latest reminder period/time in Firestore.

## 12. Inventory maintenance procedure

For every proposed feature:

1. Identify each new or changed data element.
2. Record its purpose and confirm that it is necessary.
3. Identify the data subject: child, parent, administrator, or device.
4. Identify collection point, storage system, data recipients, access roles, and countries/regions of processing.
5. Define retention and deletion behavior before implementation.
6. Determine whether parental notice/consent must change.
7. Review the SDK/provider terms for child-directed use.
8. Update Firestore rules and backend authorization if required.
9. Update this inventory, the Privacy Policy, store disclosures, and test plan.
10. Obtain technical, privacy, and legal approval before production release.
